# R2 CPU R2: reversed-order averaging only on many-option questions (vision dev, both models)

Created 2026-10-17T013235Z, commit a306b77 (clean tree). Reports; the owner picks.

## Method

- Image dev collects hold an identity and a reversed read per row. Arm `geK` uses both reads when the row has n >= K options, else identity only; `both` uses both on every row (= `vision_offline.py --arm text --orders identity+reversed`, checked equal row by row).
- All arms use the shipped text choice T (fitted under identity orders; `vision_offline` warns on that) and `gateway.decide.blend`.
- `blend` already is the arithmetic mean of per-order softmax(logprobs / T), mapped back to caller order (`orders.average_back`), so the brief's "average probabilities instead" variant is identical and is not repeated.
- Index Δ, per-benchmark Δ skill, agreement, McNemar: `vision_compare.py` (10,000 group resamples, seed 0); ΔECE/ΔNLL CIs from the same draws (`calstats.py`).

## Notes

- Six arms per model are compared against one baseline on the same rows; the CIs are per-arm, not adjusted for the number of arms looked at.
- `b / c` = rows right only under identity / only under the arm.
- Mean input tokens count each arm's own reads (the reversed read adds its suffix only: images are shared).
- The text T was fitted for one identity read. Averaging two orders lowers top-p: that helps gemma, which is overconfident at its text T on images, and hurts qwen, which is already calibrated at its text T. No T was refitted for the averaged arms here.
- qwen3.8 pads its prefix (800-token blocks): per `docs/background/vision-experiments.md` §3 an identity+reversed read on a padded profile is not live-equivalent, so qwen's two-order arms are an offline estimate of what a live two-order request would read.
